# Hold a SPI device's chip select across transfers

- Status: Accepted
- Date: 2026-11-27 19:15 UTC
- Decided by: agent

## Context
A BlueNRG-2 transaction takes the chip select low, waits for the chip to
raise IRQ, exchanges a header that says how much the chip can take or has
to give, then moves the packet, all with the chip select low (DS13280,
6.5). The SPI class asserted the chip select for one list of transfers
only, so the wait and the decision between header and packet could not
happen with it held. Zephyr has `SPI_HOLD_ON_CS` with `SPI_LOCK_ON` for
the same reason.

## Decision
`pbl_spi_hold()` takes the bus for a device, configures and enables it and
asserts the chip select; transfers with that device then run without
taking the bus or touching the chip select, until `pbl_spi_release()`
deasserts it, disables the bus and gives it back. Holds do not nest.

## Consequences
Other devices on the bus wait while a device is held; SPI1 has only the
BlueNRG-2. The drivers of the other boards are unchanged.
